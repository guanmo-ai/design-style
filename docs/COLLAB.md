# 协作方式

这个项目由一个人定方向、两个 Agent 分工完成。本页写清楚谁做什么、东西放哪、交接怎么交，以及公开仓库里什么能写、什么不能写。

## 谁做什么

| 角色 | 负责 | 不负责 |
|---|---|---|
| **观默** | 选题方向、审片、决定上架和发布 | — |
| **Claude** | 设计和短片：选题研究、候选图、分镜、动效、配乐、风格图、`PROCESS.md`、交接单 | 上架、Release、画廊登记 |
| **Codex** | 工程和上架：正式目录、Release 附件与校验、画廊登记、README 拼图、发布核验、工具与依赖、CI | 改动成片的画面和声音 |

**要在主人电脑上做的事**都交给 Codex，主人只看片、听声音、拍板。这些事包括用已登录的浏览器操作、改 Release、合并到 `main`、推送 Claude 会话管不到的分支。Claude 把这类事写进私有仓库的 `todo.md`，写成 Codex 照着做就行的步骤（命令、预期结果、出错时停在哪里）；Codex 开工先看那里。

Codex 上架时**直接采用 Claude 交的成片**，不转码、不改音画。上架时发现成片有问题，写进交接单的“上架时发现的问题”，交回 Claude 修改。

## 一期从开工到上架

1. **选题**：Claude 先读私有仓库的 `preferences.md`，再按作品名查 `works/`，有旧记录就接着做。
2. **制作**：按 `.claude/skills/style-film/` 做。草稿和成片放 `drafts/<短名>/`，推到 Claude 自己的分支。
3. **交片**：Claude 在 `drafts/<短名>/HANDOFF.md` 写交接单（`new_film.mjs` 会生成模板），只写技术事实：成片路径、SHA-256、规格、来源提交、`smooth.py` 结果、看过什么、没验证什么、上架还缺什么。
4. **审片**：观默看片、听声音。反馈由收到的那个 Agent 记进私有仓库 `works/<短名>.md`。公开的 `PROCESS.md` 只把它写成设计上的改动和理由。
5. **上架**：观默审片通过后，在私有仓库 `works/<短名>.md` 写下“审片通过 + 日期 + 版本（提交或 SHA-256）”，或者直接让 Codex 上架。Codex 按交接单上架，发布记录写进 `docs/reviews/`，并照惯例更新 `docs/HANDOFF.md`。
6. 公开的提交说明、Release 正文写“上架 xx 第 N 版为风格 NNN”，不写是谁批准的。

## 公开和私有的分界

公开仓库 `guanmo-ai/design-style` 写给读者；私有仓库 `guanmo-ai/design-style-private` 写给自己和 Agent。

| 放公开仓库 | 放私有仓库 |
|---|---|
| 作品、规格、源码、数值、配色、字体 | 主人的原话、评价、语气 |
| 设计取舍，用设计理由来写 | 审片过程：哪一版没过、为什么没过 |
| 做法、踩过的坑、验证结果 | 审片通过与发布授权的记录 |
| 公开的选题和风格介绍 | 选题范围的内部约定、未公开的取舍 |
| | 本机路径、备份位置、邮箱、账号信息 |

**把反馈改写成设计理由**：把审片意见写成画面上的事实和改法，不写是谁、在哪一轮提出的。比如“开头 1.5 秒才出现第一个动作，改成第 0 帧就落下第一张纸，0.2 秒内有动势”。

## 写公开内容的硬规则

这些规则适用于提交说明、PR 标题和正文、评论、Release 标题和正文，以及公开文档和代码注释。

- 只写改了什么、怎么做的、验证到哪一步。
- 不引用、不转述主人的话，也不写哪一版没过、谁确认了、谁批准发布。
- 不写本机路径、邮箱、备份位置。
- **少开 PR。** 草稿要审片时，推到分支，把成片路径或链接直接发给主人。确实要开 PR 时，按 `.github/pull_request_template.md` 写。
- 拿不准的句子放私有仓库。

## 自动检查

| 检查 | 什么时候跑 | 查什么 |
|---|---|---|
| Claude 钩子 `.claude/settings.json` | Claude 执行 `git commit`、写 GitHub 的 `gh` 命令、写公开仓库文件之前 | 写法规则，命中就拦下 |
| CI `.github/workflows/privacy.yml` | 每次推送、PR 打开或编辑、Release 发布或编辑 | 提交说明、PR 标题和正文、新增的文档与注释行、Release 正文 |
| `npm run privacy:check -- --text < 文件` | 手动 | 同一套写法规则 |
| 私有仓库 `tools/scan_public.py` | 上架前、定期 | 按私有记录里的原话逐句比对公开仓库、各分支、提交说明、PR、评论和 Release |

写法规则在 `scripts/privacy/check.mjs`。规则里只有写法，没有任何原话；原话比对只在私有仓库里做。

## 万一已经公开了

- **PR 正文**：改掉之后，网页上正文旁边的“edited”历史仍能看到旧版。要在网页上打开这段历史，逐条删除修订（Delete revision from history）。
- **Release 正文**：没有公开的修改历史，直接改掉就行。
- **提交说明、旧文件**：已经进了 Git 历史，只能重写历史，代价很大。所以重点放在提交之前拦住。
- 改完以后在私有仓库跑一次 `tools/scan_public.py`，再记一笔。

## 云端会话怎么用两个仓库

- Claude 云端会话：用 `add_repo` 加上 `guanmo-ai/design-style-private`，克隆到公开仓库旁边的 `design-style-private/` 目录。私有仓库自己的 `AGENTS.md` 写着怎么记录。
- 两个仓库都推到会话分支，交付时提醒主人合并。私有记录没合并之前，下一个会话看不到。
- Codex 在本机工作时，两个仓库并排放；在云端时同样先加上私有仓库。
