# 用 GPU 做动效（第六轮的经验）

> 主人 2026-11-06：“这一次效果都不错，是不是以前被仓库给限制住了？仓库有没有优化空间？”——这份文档回答第二个问题，给之后每一期用。

## 为什么这一轮上限高了

之前的片子大多是 SVG / Canvas 2D / Remotion 的 DOM：画的是**平面图形**，动的是位置、缩放、颜色。这正好适合包豪斯、孟菲斯、波普这类“平涂 + 几何”的风格，但也把题材锁在了这里。

第六轮的三个风格本体都离不开“光”：镜面反射（液态金属）、几百万个点的遮挡和景深（点云）、温度的扩散（热成像）。这些只能**真算**：光线步进、深度测试、物理模拟。云端没有显卡也没关系——Chromium 自带的 SwiftShader 能跑 WebGL2，只是慢，得会省。

## 建议（按收益排序）

1. **选题多一条线：“动起来才成立”的材质 / 媒介。** 液体、点、温度、流体、布料、玻璃、粒子、光……它们的“代表作”就是那条物理规律，动效本身就是内容。20 世纪的平涂运动照样做，两条线交替。
2. **先定签名物理，用真的方程。** 弹簧（ζ、频率）、表面张力（smin 的 k、瑞利–普拉托的 λ）、扩散（D、k）。参数直接标在画面左下角——设计师拿走就能用，这是“对设计师有帮助”最省力的做法。
3. **一个共享的 GPU 工具箱，而不是每期从零写。** 现在有：
   - `drafts/_lib/glkit.js`：着色器、浮点缓冲、分块绘制、泛光 + ACES、文字 → 距离场
   - `drafts/_lib/film-gl.cjs`：WebGL 页面逐帧截图（`window.frame(f)` 是时间的纯函数；多页并行；已渲的帧跳过，断了能接着渲）
   - `drafts/_lib/contact.py`：抽帧拼联系表，一分钟内看完整片的节奏
   - 每个风格自己的渲染器（`liquid-chrome/chrome.js`、`point-cloud/pc.js`、`thermal/thermal.js`），图和片子共用同一份
4. **审片流程：** 半分辨率、每 15 帧一张出联系表（约 1 分钟）→ 关键帧全分辨率单帧检查 → 后台全片渲染 → 配乐读同一份 `timeline.js` → 合成。
5. **配乐不变**：继续用 `drafts/_lib/song.py`（一整首歌、换章只换和弦、音效按帧号对齐）。

## SwiftShader 上的性能坑（实测）

| 现象 | 原因 | 做法 | 效果 |
|---|---|---|---|
| 空背景也要 2 秒 / 帧 | 大着色器在每个像素上都贵 | 同一份代码编译两遍：“背景版”编译期去掉步进；完整版只画物体投到屏幕上的矩形 | 6 s → 1—4 s |
| 包围盒比物体大一倍 | 半径算了两次 | 先展开到角点，角点半径记 0 | 矩形面积 ÷ 4 |
| uniform 数组很慢 | 动态下标 | 数据放进浮点纹理，`texelFetch` | 小幅 |
| 加法混合整屏发白 | 近处的点又大又多，能量按面积叠 | `a *= min(1, 9 / size²)` | 不再发白 |
| 截图 0.9 s / 帧 | PNG 编码 | 中间帧用 JPEG q95 | 0.3 s |

整片（1080 帧）液态金属约 1 小时、点云约 1 小时，两部可以同时在后台渲。
